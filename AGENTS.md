# Project collaboration

Read `HANDOVER.md` at the start of a new session, then `docs/backlog.md` and the chapters relevant to the current task. Treat the current user's instructions as authoritative if they change the recorded plan.

This project is currently in game-concept and documentation development. Do not start game implementation merely because it appears in the backlog. The intended single-page HTML/JavaScript delivery is a later constraint.

The user wants substantial explanations of the game concepts, including actor motives, player choices, institutional limits, and consequences. Keep chat handoffs concise and place long specifications in the documentation.

End each substantive handoff with concrete next-step options and clearly mark the preferred option. Preserve choices the user has already made rather than asking them to select again. The complete-turn walkthrough is queued next after the handover; the other backlog items are deferred.

Distinguish accepted direction, working proposals, historical facts, and fictional examples. Do not invent researched nation profiles or calibrated simulation results.

When asked to update the published documentation, update affected chapters consistently, commit and push the authorized changes, wait for GitHub Pages deployment, and verify the live pages and links. Preserve unrelated user changes. Check current permissions and authentication; do not assume a previous session's tool access persists.

Keep `HANDOVER.md` and `docs/backlog.md` current when the project state, accepted decisions, or next task changes. Do not mark an interactive walkthrough complete before the user has made its decisions and reviewed its outcome.
